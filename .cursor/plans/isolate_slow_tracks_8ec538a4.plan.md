# Isolate Slow Tracks from Each Other超## Why one track stalls the rest today`AsyncDetailFetcher` already runs offline `fetch_detailed_data` on a background pool, but that only covers half the pipeline. Two shared choke points remain:```mermaidflowchart LR  scroll[PanOrZoom] --> schedule[StaggeredUpdateTimers]  schedule --> live[LiveFetchViewportData SYNC]  schedule --> offlineFetch[OfflineFetch Async OK]  offlineFetch --> paint[_render_detail SYNC]  live --> paint  paint --> uiThread[QtUIThread]```1. **Live path is synchronous on the UI thread** — when `_uses_viewport_detail_fetch()` is true, [`TrackRenderer.update_viewport`](pypho_timeline/rendering/graphics/track_renderer.py) calls [`_refresh_live_detail_in_viewport`](pypho_timeline/rendering/graphics/track_renderer.py) which runs `fetch_viewport_data` (including STFT) then paints immediately. 2. **All painting is on the UI thread** — offline cache hits and `detail_data_ready` both call `_render_detail` / `setImage` / `setData` on the event loop. A heavy multi-channel EEG or spectrogram paint blocks every other track’s timer. 3. **Shared global pool** — [`AsyncDetailFetcher`](pypho_timeline/rendering/async_detail_fetcher.py) uses `QThreadPool.globalInstance()`, same pool as Add Track workers, so a slow spectrogram fetch can starve lighter track fetches. The 1 ms stagger in [`_schedule_track_group_window_update`](pypho_timeline/rendering/mixins/track_rendering_mixin.py) only spaces *scheduling*; it does not isolate work.Prior fluidity work (`.cursor/plans/live_timeline_fluidity_fixes_f4cfa3b5.plan.md`) already cut redundant updates; the remaining gap is true off-thread compute + budgeted paint.---## Approach (concrete)### Phase 1 — Live viewport fetch off the UI threadReuse the existing worker/queue pattern in [`async_detail_fetcher.py`](pypho_timeline/rendering/async_detail_fetcher.py):- Add a `ViewportFetchWorker` (or generalize `DetailFetchWorker`) that calls `datasource.fetch_viewport_data(start, end)` and queues `(track_id, range_key, data, error)`.- From `_refresh_live_detail_in_viewport`, **enqueue** instead of calling `fetch_viewport_data` inline; on result, apply only Qt graphics updates (`setImage` / `_update_live_spectrogram_image` / plot `setData`).- Coalesce by `track_id`: newer viewport request cancels/supersedes the pending one for that track (same idea as interval cancel today).- Keep datasources thread-safe for read-only ring-buffer / cache access (spectrogram STFT should not mutate shared Qt objects from the worker).- Extend tests in [`tests/test_async_detail_fetcher.py`](tests/test_async_detail_fetcher.py) for cancel-on-stale and ready-callback delivery.**Effect:** a slow live spectrogram/EEG compute no longer freezes other tracks’ event-loop turns during fetch.### Phase 2 — Budgeted UI paint so one `_render_detail` cannot monopolize the loopIn [`TrackRenderer`](pypho_timeline/rendering/graphics/track_renderer.py) / mixin:- Introduce a shared main-thread **render queue** (track_id + work item: cache-hit render, live image apply, etc.).- Drain with a time budget per turn (e.g. ~4–8 ms), then `QTimer.singleShot(0, ...)` to continue; fair round-robin across tracks so one dense EEG track cannot starve a light log track.- Defer cache-hit `_render_detail` onto that queue instead of calling it inline inside `process_viewport_update` (today’s immediate paint on cache hit is a main-thread stall).- Optional cheap win: skip or downsample paint when the interval’s pixel width is below a threshold (TODO already noted near `update_viewport`).**Effect:** slow *rendering* yields the event loop so other tracks keep updating.### Phase 3 — Separate / prioritize the thread pool- Give `AsyncDetailFetcher` a **dedicated** `QThreadPool` (not `globalInstance`), sized for viewport work.- Cap concurrent workers **per track** (e.g. 1–2) so one spectrogram track cannot occupy all workers.- Keep Add Track on the global pool (or a second dedicated pool) so menu-time compute cannot starve scrolling.---## Files to touch- [`pypho_timeline/rendering/async_detail_fetcher.py`](pypho_timeline/rendering/async_detail_fetcher.py) — viewport worker, dedicated pool, per-track concurrency- [`pypho_timeline/rendering/graphics/track_renderer.py`](pypho_timeline/rendering/graphics/track_renderer.py) — async live refresh; enqueue paint- [`pypho_timeline/rendering/mixins/track_rendering_mixin.py`](pypho_timeline/rendering/mixins/track_rendering_mixin.py) — own/share the render-budget pump with the fetcher- Datasources that do heavy live work (notably LSL spectrogram in `specific/lsl.py`) — ensure `fetch_viewport_data` is safe off-thread- Tests: `tests/test_async_detail_fetcher.py`, plus a small render-queue fairness test if practical---## Out of scope / non-goals- Moving Qt/pyqtgraph painting itself off the UI thread (not supported; budgeting is the right model).- Full multiprocess isolation (overkill vs QThreadPool for this GUI).- OpenSpec proposal (no openspec tree in pyPhoTimeline).---## Success criteria- Panning with a heavy live spectrogram track: other tracks (log, motion, overview) continue to refresh without multi-frame freezes.- Offline: a track with many cache-miss fetches does not prevent lighter tracks from painting as their data arrives.- Add Track heavy compute does not pause viewport fetches for existing tracks.
